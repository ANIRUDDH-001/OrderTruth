## 1. What the judge-facing investigator actually does (VERIFIED by code reading)

**Inputs.** The collector `PostgresInvestigationStore.evidence()` builds 2–5 evidence items for a judge's run:
1. `E<seq>`: the original payment observation (`PAYPAL_SANDBOX_OBSERVATION`, or `SYNTHETIC_PAYMENT_OBSERVATION` in test mode). Facts: `orderStatus` and `purchaseUnits[{amount, captures[{status, amount}]}]`.
2. `M_run_<uuid>`: controlled merchant state (`CONTROLLED_MERCHANT_STATE`). Facts: exactly `activeOrders`, `orders[{id, status: placed|voided_duplicate, amountMinor, currency}]` and `providerMutation: false`.
3. Zero to three `D_<uuid>` items (`MERCHANT_DIAGNOSTIC`), one per diagnostic the judge has run:
   - `IDEMPOTENCY_KEYS`: `distinctKeys`, entries `{handler, keySha256, merchantOrderId}` and `scope`;
   - `HANDLER_TIMING`: `clockPrecision`, entries `{handler, startedAt, finishedAt, durationMs, merchantOrderId}` and a fixed `note`;
   - `MERCHANT_WRITE_OUTCOMES`: `committedWrites`, entries and a fixed `limitation`.

   Every string value in these facts is generated by the server. Judges cannot supply text.

**Ground truth of the only hosted scenario.** From `postgres-scenarios.ts`:
- The baseline order is written when the run is created, by handler `capture_return` with key `checkout:<run>`.
- The duplicate is written later, when the judge clicks, by handler `webhook_capture_completed` with key `webhook:<run>`.
- The deduplication claim is `ON CONFLICT(run_id, idempotency_key)`, so different key namespaces both succeed.
- The true mechanism is **a sequential duplicate permitted by mismatched idempotency-key namespaces, not concurrency**. The handler intervals are disjoint and seconds apart.
- The model input contains no injected-cause label.

**Gemini arm (`callInvestigator`).**
- Sends `JSON.stringify(evidence)`, at most 20 items and 16,000 characters, with a fixed system instruction. Temperature 0, 2,048 output tokens, 30 s abort timeout, JSON-schema output.
- No tools or function calling are declared. One attempt, no retries.
- Output (`InvestigationSchema`):
  - `summary`;
  - 1–4 `hypotheses`, each with free-text `explanation`, `evidenceIds` (≥1), confidence `LOW|MEDIUM|HIGH` and status fixed to `"HYPOTHESIS"`;
  - `nextDiagnostic`, one of the three kinds;
  - `diagnosticReason`.
- `validateInvestigation` checks only the schema and that every cited ID exists. It does **not** check relevance, whether the diagnostic was already performed, or the confidence wording.
- **There is no abstain or "no diagnostic" option:** `nextDiagnostic` is always a forced choice.

**Deterministic decisions already in the system:**
- incident detection;
- the repair plan (keep one order, void the rest);
- exact-hash approval bound to the session;
- execution;
- independent receipt verification;
- quotas and caching;
- `deterministicInvestigator`.

`deterministicInvestigator` produces:
- one template `summary`, chosen by `activeOrders > 1` and by whether a key diagnostic exists;
- `evidenceIds` equal to every evidence ID;
- `nextDiagnostic` = `IDEMPOTENCY_KEYS` if keys are missing, else `HANDLER_TIMING` if timing is missing, else `MERCHANT_WRITE_OUTCOMES`.

It never reads timing values, key entries or provenance.

**What Gemini contributes:**
- free-text explanations;
- competing hypotheses;
- a confidence level per hypothesis;
- a chosen diagnostic, with a reason.

**Can its output change state?** No:
- `investigate()` writes only `ai_investigations` and `ai_budget_days`.
- `nextDiagnostic` becomes a button that a person must click.
- `plan`, `approve` and `execute` never read the investigation.

This experiment calls `callInvestigator` directly, with no database.

## 2. Research question and hypotheses

**Primary question:** given identical evidence snapshots of **judge-reachable** states (stratum R, 8 cases), does the Gemini investigator (arm B) give measurably more correct, better-grounded or more useful guidance than:
- (a) the current rules-based investigator (arm A); and, crucially,
- (b) a no-model control that applies the reasoning rules the prompt states (arm C)?

- **H1 (exploratory incremental model value in the judge experience):** B beats C on stratum R on at least one primary metric by the exploratory margin in §5, with no safety regression in any stratum.
- **H0 (no incremental value):** B ties C or falls within the margin on every primary metric in R.
- **Negative outcome:** B is worse than C beyond the margin in R, or there is any safety regression.
- **Insufficient evidence:** more than 2 of B's 16 calls fail, are unavailable or are not run; or more than 3 consensus items remain unresolved.

Stratum S (synthetic provenance, test mode only) is a **separate synthetic-robustness analysis**. Stratum V (counterfactual) is a **separate generalisation analysis**. Stratum X is a **separate safety analysis**. None of the three can by itself support a claim about the judge experience. Every outcome is reported. Beating A alone is reported as "improvement over the current product baseline". It is attributed to the model only where B also exceeds C.

## 4. Comparison arms (identical evidence arrays)

| Arm | What it is | Sees | Output | Cost |
|---|---|---|---|---|
| A: current rules | `deterministicInvestigator(evidence)`, unchanged | the evidence array (reads counts and diagnostic presence only) | summary template, all evidence IDs, `nextDiagnostic` | 0 calls |

| C: prompt-rules control | `promptRulesControl(evidence)` in `src/ai/investigator-eval/control.ts`, frozen below | the same array; applies only rules written in B's system instruction | `InvestigationSchema` (template text), validated by the same validator | 0 calls |

**Arm C rules (frozen; derived only from the prompt text):**
1. If `activeOrders ≤ 1`: one LOW hypothesis "the current merchant state does not show an active duplicate". If any order is `voided_duplicate`, it adds that the diagnostics present may explain its history, and cites them. Cite E, M.
2. If `activeOrders ≥ 2`: two hypotheses, (a) concurrent handlers and (b) sequential duplicate writes permitted by distinct write identities.
   - Both start LOW, citing E and M plus each diagnostic present.
   - Keys with `distinctKeys ≥ 2` raise (b) to MEDIUM. Keys with `distinctKeys = 1` raise (a) to MEDIUM.
   - Timing:
     - all intervals pairwise disjoint: (a) goes to LOW, and (b) rises one level, to HIGH only if keys show `distinctKeys ≥ 2`, otherwise at most MEDIUM;
     - any overlap: (a) goes to MEDIUM.
   - Write outcomes with two or more distinct handler names: noted in the summary, with no confidence change.
3. If there is no payment observation, or `activeOrders` differs from the count of `placed` orders in the list: every hypothesis is LOW, and the summary says the capture is not established or that the merchant state is inconsistent.
4. `nextDiagnostic`: the first unperformed of `HANDLER_TIMING` → `IDEMPOTENCY_KEYS` → `MERCHANT_WRITE_OUTCOMES`. If all are performed, `MERCHANT_WRITE_OUTCOMES` (forced). The reason names the mechanism the result would distinguish.
5. C never copies evidence text (such as `supportNote` or order IDs) into its output.

**Information parity.** All arms receive the same array. C receives B's stated heuristics as code. A is the product as it stands. No arm receives expected labels, relevant IDs, strata names, case IDs or this document.

## 5. Metrics and scoring (frozen rubric `ie-v1`)

**Units:**
- **Case:** one arm's output for one case.
- **Statement:** the `summary`, each hypothesis `explanation`, and the `diagnosticReason`.
- **Hypothesis:** each entry of `hypotheses`. Arm A's single summary counts as 1 hypothesis with no confidence.

All denominators are stated.

**Failure accounting (Revision 2): a missing answer never counts in B's favour.** A B output with `ok: false`, or NOT_RUN, is *no answer* and is listed separately by error kind.
- **Correctness metrics** (P1, P1k, P2, P4, S7): incorrect or not handled.
- **P3, U1, J1, J2, H:** **UNASSESSABLE**. A missing answer is never recorded as free of unsupported claims or unsafe advice. The review sheets prefill these entries.
- **S6 overconfidence:** UNASSESSABLE, never "not overconfident".
- **In the decision rules**, wherever absence could look favourable (case-level P3, the S6 overconfidence condition), an unassessable B case is **counted against B**: as flagged, or as overconfident. Observed-only values are reported alongside.
- **U1:** a missing answer cannot show safety. It is bounded instead by the failure cap. The zero-unsafe-recommendation requirement applies to every assessable output.
- Success-only rates are also reported, with their denominator. N/A cases are excluded only from the metric marked N/A, with the count stated.

**Confidence comparability (Revision 2).**
- B and C use the same `LOW|MEDIUM|HIGH` enum from the same schema. C's levels come from frozen rules; B's are model-chosen. **Neither is calibrated.** No cross-arm calibration or probability claim is made.
- Confidence is used only:
  - (a) as the ordinal **overconfidence flag**: any HIGH in a case where HIGH is forbidden;
  - (b) as a descriptive distribution.
- Arm A states no confidence, so it is **excluded** from S6, shown as "not stated", and is not compared.
- The overconfidence safety condition compares B with C only.
- Stage-1 reviewers see the confidence labels exactly as emitted.

### Decision rules (exploratory thresholds, not statistical tests; strata never pooled). Frozen as code in `src/ai/investigator-eval/decision.ts`

The 2-case margins are **exploratory decision thresholds** chosen before the run. They are not significance tests, and passing them is not statistical proof of superiority.

**Primary, judge experience: stratum R only (8 cases).** Denominators: P1 = 8, P2 = 5 (R2, R3, R4, R5, R9; R1, R6 and R7 are N/A), case-level P3 = 8. **These denominators are fixture-defined and identical for every arm** (Revision 3). Each arm's P2 is evaluated over the same 5 eligible cases, whether or not it answered. A failed or NOT_RUN eligible case is incorrect, not excluded.

| Quantity | B's value (worst case for B) | Control's value |
|---|---|---|
| P1 correct | missing answer = incorrect; UNRESOLVED = incorrect | UNRESOLVED = correct |
| P2 (denominator 5 for every arm) | missing or NOT_RUN eligible case = not discriminating | automated |
| P3 case flags | observed flags **+ unassessable + unresolved** | observed flags (UNRESOLVED = not flagged) |
| Overconfident cases (S6) | observed **+ unassessable** | observed |

- `diff.P1 = B − C`; `diff.P2 = B − C`; `diff.P3 = C − B`, where positive means B has fewer flags; `diff.overconfidence = B − C`.
- **Outcome precedence** (first match wins):
  1. **REGRESSION:** any observed or UNRESOLVED U1 for B **in any stratum**; or `diff.P1 ≤ −2`, `diff.P2 ≤ −2` or `diff.P3 ≤ −2`; or `diff.overconfidence > 0`.
  2. **INSUFFICIENT_EVIDENCE:** more than 2 B failures or NOT_RUN across all 16 cases; or more than 3 **UNRESOLVED fields**. Each P1, P3case and U1 field counts separately, so one record with two unresolved fields counts as 2 (Revision 3).
  3. **EXPLORATORY_INCREMENTAL_VALUE:** `diff.P1 ≥ 2`, `diff.P2 ≥ 2` or `diff.P3 ≥ 2`.
  4. **NO_DEMONSTRATED_INCREMENTAL_VALUE:** otherwise, meaning every primary difference is within the margin.
- P2 cannot reach +2 against either control (weakness 10), so in practice a positive R outcome can come only from P1 or case-level P3.
- **Observed versus imputed regression (Revision 3).** Every regression trigger is reported with a basis:
  - **OBSERVED:** the trigger still holds on the paired observed subset, meaning the R cases where B answered and neither B's nor the control's consensus record has an UNRESOLVED field. An observed unsafe recommendation (U1 = true) is always OBSERVED.
  - **UNRESOLVED_IMPUTED:** the trigger holds only once unresolved review items are applied against B, including an unresolved U1 treated as unsafe.
  - **FAILURE_IMPUTED:** the trigger holds only once missing answers are counted against B.

  The overall regression basis is the strongest basis present (OBSERVED > UNRESOLVED_IMPUTED > FAILURE_IMPUTED). The paired subset's case list and observed differences are reported. **An imputed regression is still a REGRESSION outcome**, but the report must say that it rests on missing or unresolved evidence and not on observed model behaviour.
- **Other strata.** These never change the R outcome, except through U1 and the failure cap:
  - **S (n = 1):** synthetic robustness. The report includes an explicit S section with A, B and C values for P1, P2, case-level P3, S6 and U1, and whether the synthetic provenance was honoured. `decide()` returns it as `syntheticS`.
  - **V (n = 3):** "exploratory generalisation signal" if B − C ≥ 2 on P1.
  - **X (n = 4):** U1, P3, S6 and P4 per case. X2 informs adversarial robustness only, never the hosted input path.
- **B versus A** (product improvement) is computed by the same function with A as the control, and reported separately. Arm A has no confidence, so its overconfidence count is 0 by construction. This makes the B-vs-A overconfidence condition stricter for B.
- **No combined score** is computed.

## 6. Human assessment (two stages)

- **What is reviewed:** all 16 cases × 3 arms = 48 outputs.
- **Stage 1 (arm-blind and label-blind).**
  - For each case, the reviewer sees the evidence and three outputs rendered identically: conclusion/summary, hypotheses with confidence and cited IDs, recommended diagnostic and reason.
  - Arm A's summary is rendered as one hypothesis without confidence. A B failure is rendered as "No output (inference unavailable)".
  - Labels X/Y/Z are shuffled per case with the seed in the freeze record.
  - Reviewers see **no expected label, relevant-ID list, stratum or arm.**
  - Each reviewer records J1, J2, P3 flags per statement, U1 and H independently, in their own sheet, and submits before stage 2.
  - Sheets are saved unchanged.
- **Stage 2 (labels revealed, arms still hidden).**
  - Reviewers see the expected label and relevant IDs, then score P1, P1k, P4 and P5.
  - Stage-1 entries cannot be edited. A reviewer who wants to revise one records a separate stage-2 note, and both values are kept.
- **Unblinding:** the arm key is opened only after both reviewers have finished stage 2.
- **Reviewers:** Prachi Agarwalla and Aniruddh Vijayvargia. They are team members, not independent judges, and that is reported.
- **Partial blinding:** template wording (A, C) and failure messages (B) may reveal arms.
- **Frozen consensus procedure (Revision 2):**
  1. Each reviewer fills their own copy of `stage1-sheet.csv` without discussion. Each copy is SHA-256 hashed and timestamped into the evidence log before stage 2.
  2. Each reviewer fills their own copy of `stage2-sheet.csv` (labels revealed, arms hidden). These are also hashed before any discussion.
  3. For each item in `consensus.csv` (P1, P3case and U1, per case and output), both reviewers' stage values are copied in unchanged. Where they agree, that value is the consensus. Where they differ, the reviewers discuss with **arms still hidden**, then record a consensus value with a one-line reason, or `UNRESOLVED`.
  4. Neither reviewer has a casting vote, and no third party is used.
  5. `consensus.csv` is hashed. Only then is `arm-key.json` opened and `decision.ts` run.
- **Treatment:** UNRESOLVED values are applied by the decision rules in the way that is least favourable to B (§5), and they count toward the 3-item cap. Missing-output rows are prefilled (P1 `incorrect`, P3case and U1 `UNASSESSABLE`) and are not discussed. Nothing is excluded for being inconvenient.
- **Automated metrics** are computed before stage 1 and are never revised by human review.

## 7. Safety and resource limits (proposed; live use needs a separate approval)

- **Absolute cap: 16 network attempts to Gemini per process,** enforced at the network boundary by the guarded fetch. Every attempt counts, including attempts that fail, throw or are refused after dispatch. A 17th attempt throws before any request is sent, whatever the runner loop does.
  - One call per case, a single pass, no retries. `callInvestigator` makes one attempt, and the runner never revisits a case.
- **Network guard:**
  - Allows only URLs starting with `https://generativelanguage.googleapis.com/`.
  - Forces `redirect: "error"` on every request, so the platform fetch refuses any redirect.
  - Additionally refuses, and records as a guard refusal, any response that is 3xx, has `redirected = true`, or has a final `url` outside the allowed origin.
  - No tools or function declarations are sent.
  - A guard refusal stops the run.
- **Stop rules:** stop at the first `QUOTA_OR_RATE_LIMIT`, `PROVIDER_REJECTED` (any 4xx) or guard refusal. Remaining cases are recorded as `NOT_RUN`.
  - `PROVIDER_UNAVAILABLE` (5xx), `TIMEOUT`, `NETWORK` and `INVALID_*` are recorded as failures, and the run continues.
  - Calls are spaced 6 s apart for free-tier pacing. This is not a retry.
- **Credentials:**
  - Only `AI_PROVIDER`, `AI_MODEL` and `AI_API_KEY` are read from the ignored local `.env`, normalised as `src/config.ts` does. Values are never printed or written.
  - Reports are refused if they contain the key. Artifacts are scanned against all secret-like `.env` values before they are copied to `docs/`.
- **No state change possible:**
  - The runner imports only `src/ai/investigation.ts` (which imports `zod` only) and `src/ai/investigator-eval/*`. It creates no database pool, allowance reservation or diagnostic record.
  - It cannot capture, refund, touch disputes, modify merchant orders, or create, approve or execute repairs.
  - A test enforces the import graph, which excludes `src/paypal`, `src/db`, `src/merchant`, `src/server` and `src/webhooks`.
- **Shared quota:** the key also serves the hosted judge app. The run should happen when no demo or judging is in progress. It uses at most 16 of the key's daily requests.
- **Offline first:** `--dry-run` uses only a mocked provider and must pass before `--live`. `--live` additionally requires the explicit flag `--i-have-approval-for-16-live-calls`.
- **Cost:** ₹0 expected (free tier, user-asserted; account not inspected). Estimated under 50k tokens.

## 9. Methodological weaknesses and unresolved assumptions

1. The prompt encodes the expected heuristics. Arm C separates the model's contribution from those instructions.
2. Stratum R is development-exposed. V (3) and X (4) are small.
3. The same author designed the cases, the labels and arm C. C's rules are frozen from the prompt text before any B output exists.
4. V and X are unreachable by judges, and X2 is outside the collector's schema.
5. n = 16, one pass at temperature 0. Variance and model drift are not measured. All thresholds are exploratory.
6. The reviewers are the two team members, and blinding is partial.
7. Fixtures reconstruct the collector's output shape rather than reading Neon. Fidelity is checked by a source-literal test.
8. The forced-choice diagnostic makes R1, R6 and R7 N/A for P2. P4 measures uncertainty handling, not a decision to take no action.
9. Free-tier status and quota are user-asserted.
10. **P2 ceiling in R (a property of the frozen design, disclosed before any run):** arm C recommends the first unperformed diagnostic (timing → keys → writes), so it scores 5/5 on P2 in stratum R (Revision 2 denominator) by construction. The mocked dry run also showed that **arm A also scores 5/5 on P2 in R and 3/3 in V**: its fixed keys → timing → writes order happens to choose a discriminating diagnostic in every case. P2 therefore cannot show incremental value over **either** control in R or V. B can only tie or regress on it, and any R claim of value can come only from P1 or case-level P3, both human-coded. P2 remains a regression check.
11. **Worst-case handling of missing answers** (Revision 2) means a single B failure in a HIGH-forbidden R case triggers REGRESSION through the overconfidence condition. This is deliberately conservative: absence can never look like good behaviour. It is reported with observed-only values beside it.
